# G2 — BEAT fork A/B: skip the unused fused-CUDA identity cache (2026-11-13)

**Question.** Does A3 (fork branch `perf/skip-fused-identity-cache`, commit
`9ec86b0c22d65573240a36199210ada517b67928`) reduce fused-CUDA memory or wall time, with no physics change,
compared with the current pin `0850ef39b29d7c51f8fbb082184d3784d2ff8bef`?

**Verdict: the G2 adopt criterion is met** (plan §3, row G2: "peak VRAM drops, or a larger DOF now fits, with
parity inside the `docs/FORKS.md` tolerances"). Measured peak drops by **55–70 %** and per-frequency wall time by
**20–30 %** at 4.2k / 8k / 12k quarter DOF, and the analytic self-test is numerically identical on both commits.
The pin is *not* bumped by this document; that is a separate commit (see "Adopt").

## Why the saving is that large `[measured arithmetic]` — corrected 2026-11-13 after independent review

The skipped object is **two** dense complex64 device matrices, not one: `identity_p1_p1` (P1×P1 = N×N) **and**
`identity_p1_dp0` (P1 test × DP0 trial = **N×E**, where E is the number of triangles — `assemble_l2_identity_matrix`
allocates `zeros(T, test_dof_count, trial_dof_count)` and the DP0 trial space has one dof per face,
`BeatEngineCore.jl:1175-1202`; both are uploaded by `build_cuda_burton_miller_identity_cache`, `:1417-1424`).
The device payload on the fused path was therefore `8·(N² + N·E)` bytes:

| DOF (E) | `8(N²+N·E)` MiB | measured saving | ratio |
|---:|---:|---:|---:|
| 4,168 (8,105) | 390 | 384 | 98.4 % |
| 8,021 (15,722) | 1,453 | 1,388 | 95.5 % |
| 11,938 (23,487) | 3,227 | 3,150 | 97.6 % |

**This retracts the first version of this section**, which called the skipped companion "N×2" and attributed the
2.7-2.8× gap over `8·N²` to CUDA pool segment rounding. That was wrong: with E ≈ 2N the second matrix alone is ~2N²,
and the measured savings equal the nominal allocation of both matrices to within 2-4.5 %. No pool effect needs to be
invoked. The matrices are built during request setup and released only in the request's `finally`, so they are live
across the whole assembly+solve peak window (this also answers the "a freed segment could be reused" objection for
the fresh-process protocol; persistent-host multi-request behaviour is still unmeasured, see follow-up 3).
The matrices are never read on the fused path (`BeatEngineDriver.jl:757-758` is reached only from the non-fused
`else` at `:2039`), which is why removing them cannot change the answer.

## Physics parity `[measured]` — with one honest gap

`hornlab-search selftest --analytic` on both commits, after `gpu-clean`:

| commit | R(ka) spread (tol 0.5 dB) | convergence sub3 / sub4 / sub5 | result |
|---|---|---|---|
| A `0850ef39` | 0.020 dB | 0.0204 / 0.0051 / 0.0013 | PASS |
| B `9ec86b0` | 0.020 dB | 0.0204 / 0.0051 / 0.0013 | PASS |

Also identical on both: spreading 2 m→4 m = 6.0206 dB per ka (target 6.0206 ± 0.05), omnidirectionality
0.0000–0.0050 dB (limit 0.1).

**Gap (found in independent review):** `selftest.py::_spec` builds its `SolveSpec` without `cuda_fused`
(`hornlab_search/search/selftest.py:126-134`), so this test exercises the **non-fused** route. It therefore proves
the *unchanged* path is unchanged — which was already a code certainty — and says **nothing** about fused-path
output. Output equality on the fused route is a strong code argument (the fused assembler kernels are untouched and
the skipped allocation is never read) but it is **not measured**. `docs/FORKS.md` step 6.3 (a response compare
between pins) was not run. That compare is follow-up 2 below and should be done before the pin bump is called final.

**Also missing:** the plan's G2 row requires recording **dedicated + shared (WDDM)** peak. This harness records
dedicated only (`nvidia-smi memory.used`). Spill is implausible at ≤ 5.5 GB of 8 GB, but zero spill was not
demonstrated, so this evidence is one field short of full G2 compliance.


## Two artefacts that are NOT regressions

1. **`convergence level 5 not run: backend 'beat_cpu' is not available`** appeared on B after the A/B installs and
   made `sub5` read `n/a`. Cause: `pip install --force-reinstall` replaces the package directory, which drops the
   per-backend readiness marker. `python -m hornlab_beat_bem.provision --backend cpu` restores it and B then reports
   `sub5=0.0013`, identical to A. Provisioning is per backend, so the GPU runtime is unaffected.
2. **One measurement (B, 11,938 DOF, rep 0) exited 1** with `SHUTDOWN FAILED: WorkerReleaseError: BEAT host
   process(es) still alive after release: [27964]` after emitting a complete result (delta 1,343 MiB, 7.76 s/freq).
   This is the known Julia-host teardown race (`AGENTS.md` "GPU / Julia hygiene"), not a solver error; the two
   other reps of that point (1,350 / 1,338 MiB) agree with it.

## Consequence for A5 (do this with the pin bump, not before)

A5 calibrates fused memory as `4.0 × 8·N²`, from 12,183 DOF ≈ 4.7 GB measured on the **unpatched** pin. With A3 the
12k point measures **1,343 MiB**.

**Corrected after review:** do not replace 4.0 with a bare multiplicative factor. Pin B's footprint is better modelled
as `8·N² + constant overhead` — the measured deltas minus `8N²` are 187 / 212 / 256 MiB at the three points, i.e. a
roughly constant ~0.2-0.3 GiB of pool/workspace on top of the one remaining dense matrix (the ratio `delta / 8N²`
drifts 2.41 → 1.43 → 1.24 with N, which is exactly why a single multiplier is the wrong shape). Until A5.4 is wired,
A5 stays warning-only. Its `tests/test_solve_feasibility.py` case "20,237 fused → refuse" encodes pin-A arithmetic and
is now **provably stale**, but repo rule 7 forbids re-basing a test on arithmetic alone: re-base it on the measured
20k point from follow-up 1.

## Independent review (Oracle, 2026-11-13)

Verdict: **adopt-with-conditions**, confidence high (~0.85) on memory and patch safety, medium-high (~0.7) on wall
time. The review confirmed from source that the only reader of the cache is `pressure_for_drives`, with exactly one
call site inside the non-fused `else`; that `fused_burton_miller_selected` returns false without
`HORNLAB_BEAT_FUSED_BM_CUDA=1`, so the default path is byte-identical between pins; that symmetry, near-correction,
MEH/multi-channel and warm-host routes cannot reach the skipped cache; and that `julia/coupled_solver.jl:909-910`
builds its own cache but is **unreachable from the worker** (`solver.jl` includes only `BeatEngineCore.jl` and
`BeatEngineDriver.jl`; the coupled file is pulled in by tests/scripts only), so it is a dormant duplicate, not an
open second cost.

It also found the two defects now corrected above (mechanism; parity gap) and one missing field (shared-memory peak).
