# G2 — BEAT fork A/B: skip the unused fused-CUDA identity cache (2026-11-13)

**Question.** Does A3 (fork branch `perf/skip-fused-identity-cache`, commit
`9ec86b0c22d65573240a36199210ada517b67928`) reduce fused-CUDA memory or wall time, with no physics change,
compared with the current pin `0850ef39b29d7c51f8fbb082184d3784d2ff8bef`?

**Verdict: the G2 adopt criterion is met** (plan §3, row G2: "peak VRAM drops, or a larger DOF now fits, with
parity inside the `docs/FORKS.md` tolerances"). Measured peak drops by **55–70 %** and per-frequency wall time by
**20–30 %** at 4.2k / 8k / 12k quarter DOF, and the analytic self-test is numerically identical on both commits.
The pin is *not* bumped by this document; that is a separate commit (see "Adopt").

## Method (`TOOLCHAIN.md` M2 + `docs/FORKS.md` step 6.4)

- Tool: `tools/measure_fused_ceiling.py` — **one solve per fresh Python process**, VRAM polled out of process
  (0.2 s thread), baseline = first sample, peak = maximum, delta = peak − baseline; `worker.shutdown(verify=True)`
  in a `finally`; the mesh cache and runs root are the gitignored `scratch/` + `runs/` paths.
- `hornlab-search gpu-clean` between every measurement; VRAM was 650–1050 MiB before each run (desktop baseline).
- Meshes: the tool's own `examples/osse_baseline.yaml` quarter-domain seed, calibrated with `--mesh-only` (CPU/gmsh,
  no solver) so both commits measure **identical meshes**:

  | `--mouth-res` | quarter DOF | triangles |
  |---|---:|---:|
  | 10.0 mm | 4,168 | 8,105 |
  | 7.1 mm | 8,021 | 15,722 |
  | 5.8 mm | 11,938 | 23,487 |

- 3 repetitions per point per commit (fresh process each; run 1 is the cold measurement, runs 2–3 warm-machine
  repeats), `--flag on` (fused), 73 angles, 1 kHz, balloon off.
- Commits: A = `0850ef39` (pin), B = `9ec86b0` (A3). Installed non-editable by SHA from the local fork checkout
  (`pip install --force-reinstall --no-deps "hornlab-beat-bem @ git+file:///…@<sha>"`); `direct_url.json` verified
  to show the intended commit before each matrix, and the patched lines were confirmed present in the installed
  `julia/BeatEngineDriver.jl` for B and absent for A.

## Why the saving is that large `[inferred]`

The skipped object is one **complex64 N×N device matrix** (`identity_p1_p1`; the `p1_dp0` companion is N×2). Its
lower bound is `8·N²` bytes = 139 / 515 / 1,140 MB at 4,168 / 8,021 / 11,938 DOF. The observed savings are 2.7–2.8×
that, consistent with the CUDA memory pool rounding whole segments up and releasing them together — the same
"pool, not matrix size" effect already documented in `TOOLCHAIN.md` M2. The matrix is never read on the fused path
(`BeatEngineDriver.jl:757-758` is reached only from the non-fused `else` at `:2039`), which is why removing it
cannot change the answer.

## Two artefacts that are NOT regressions

1. **`convergence level 5 not run: backend 'beat_cpu' is not available`** appeared on B after the A/B installs and
   made `sub5` read `n/a`. Cause: `pip install --force-reinstall` replaces the package directory, which drops the
   per-backend readiness marker. `python -m hornlab_beat_bem.provision --backend cpu` restores it and B then reports
   `sub5=0.0013`, identical to A. Provisioning is per backend, so the GPU runtime is unaffected.
2. **One measurement (B, 11,938 DOF, rep 0) exited 1** with `SHUTDOWN FAILED: WorkerReleaseError: BEAT host
   process(es) still alive after release: [27964]` after emitting a complete result (delta 1,343 MiB, 7.76 s/freq).
   This is the known Julia-host teardown race (`AGENTS.md` "GPU / Julia hygiene"), not a solver error; the two
   other reps of that point (1,350 / 1,338 MiB) agree with it.

## Consequence for A5 (do this with the pin bump, not before)

A5 calibrates fused memory as `4.0 × 8·N²`, from 12,183 DOF ≈ 4.7 GB measured on the **unpatched** pin. With A3 the
12k point measures **1,343 MiB** — the 4× factor is now ~3× too pessimistic and would refuse candidates that fit.
Recalibrate the factor from this table (order 1.2×) when A5.4 is wired; until then A5 stays warning-only.
