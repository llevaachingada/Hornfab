# SCREEN at 12 kHz — high-frequency screening policy (2026-11-23)

Status: **complete (2026-11-24).** 24 designs × 7 arms = 162 evaluations (161 ok, 1 solve-timeout),
plus epw 5/6/8 on 4 designs. **Outcome: no default change** — see `ADOPTION_DECISION.md` and
`HANDBACK.md`; measured tables in `GPU_BENCHMARK.csv`, `SCREEN_RANKING.csv`, `HF_FAILURES.csv`,
`DECISION_TABLE.csv`.

## 0. What this pass owns and does not own

Owned: `hornlab_search/config.py` (frequency policy), frequency-specific tests, frequency
benchmark tooling, this evidence directory. **Not** owned and **not touched**: `hornlab_search/mesh/**`,
`hornlab_search/design/families.py`, the mesher's sizing algorithms, `3D` visualisation. Every mesh
in the experiment is the production `mesh.build` at the arm's own `f_max_hz` with the existing
controls (`epw`, `rear_res_factor` left at 1.0 except where an arm says otherwise).

## 1. Audited baseline (facts, not YAML intent)

`hornlab_search/config.py` at HEAD `626a7c65`:

| mode | frozen grid | code |
|---|---|---|
| screen | 500–10000 Hz, 12 points | `FREQ_GRIDS["screen"]` |
| verify | 300–16000 Hz, 25 points | `FREQ_GRIDS["verify"]` |
| final | 250–20000 Hz, 36 points | `FREQ_GRIDS["final"]` |
| finalist | 300–16000 Hz, 36 points | `FREQ_GRIDS["finalist"]` |

* `mode_freqs` clips the top edge **down** to `target.band_hi_hz`; it never extends it
  (`config.py:1888-1890`). A 12 kHz brief with the frozen screen grid therefore still solves
  12 points to 10 kHz, and the 10–12 kHz band is never solved or scored.
* `grid.screen_extra_hz` is merged into the screen grid but is itself clipped at that same
  (already clipped) top edge (`_merge_screen_extra`, `config.py:1863-1872`).
* `solve.freq_grid` **replaces every mode's grid**, not just screen (the `meh_*` configs rely on
  this). Using it for a 12 kHz screen silently collapses `verify` onto the same grid — measured:
  `meh_t1_search.yaml` resolves screen = verify = 41 points, 120–12000 Hz.
* The objective is a **per-frequency mean** of band-masked arrays (`scalar_v2._mean`,
  `objective/scalar_v2.py:80-104`), so adding points changes the arithmetic weighting, not the
  objective's magnitude scale. `n_in_band` is bookkeeping only.
* v11's four CD terms score on `objective.cd.band_hz` / `cd.offaxis.band_hz` — defaults
  700–8000 / 2500–8000 Hz (`metrics/cd.py:40-43`), pinned explicitly in every shipped v11 brief.
  A screen that solves to 12 kHz while those bands stay at 8 kHz leaves ~47 % of v11's weight
  blind to the new band. This is why the probe briefs extend the CD bands as well.
* `solve/feasibility.py` is arithmetic only and has **no production caller**; the enforced limit
  is the dof cap (`mesh/build.py:271-281`, `417-426`). `allow_large_mesh` is hard-coded False.
* Score identity: `SolveSpec.hash()` includes the exact `freqs_hz` (`types.py:108-111`);
  `MeshSpec.hash()` includes `f_max_hz` (`types.py:52-71`). `config_sha` (CMA resume) hashes the
  raw config, so a grid change is a new run identity. **Gap found and fixed:** warm start compared
  only objective version + brief payload + family + knob names, and the brief payload does not
  carry `solve.*grid` — two configs with different solved frequencies could share stored J.
  `search/warmstart.py` now compares a `_grid_key` of `solve.screen_grid` / `solve.freq_grid`

### 1.2 What was already known (and what was not)

From `docs/evidence/HF12K_VERIFY_2026-10-23.md`, `FUSED_CUDA_2026-10-24.md`,
`MEASUREMENT_PACK_2026-10-24.md`, `docs/evidence/b1_mesh_2026-11-18/README.md`,
`docs/research/senior_pass_2026-10-24/03_HIGH_FREQUENCY_12KHZ.md`,
`scratch/fable_architecture/FREQUENCY_BUDGET.md`:

* 12 kHz **verify** solves succeeded on 14 small designs (25 freqs, 1 024-pt balloon): 31–83 s per
  design, dedicated peak up to 7 360 MiB above a 341 MiB baseline on the non-fused path at
  6 049 DOFs. Fused re-solves: 4 438 DOFs / 8 626 tris, mesh 8.0 s, solve 52.9 s, 672 MB process
  probe. EPW 6 vs 7/8 converged downward to ≤0.06 dB on-axis, ≤0.31° beamwidth for those sizes.
* **No dense independently-solved 12 kHz reference exists anywhere in the repo.** The only
  ranking/subsampling numbers (`FREQUENCY_BUDGET.md`) are 350–8 000 Hz interpolation from stored
  18/29-point responses — explicitly not ground truth.
* No top-N / Spearman comparison between a 12 kHz screen and a higher-fidelity reference exists.
* Known limits: fused ceiling evidence at 12 183 DOF (4 744 MiB, 13.7 s/freq) and failure at
  20 237 DOF; MEH walls at a 12 kHz request validate only to ~6.0 kHz (`MEH_M8_2026-10-31.md`);
  a 0.28 m² horn would need ~34 k DOFs at 12 kHz (infeasible on 8 GB).
* f11 (1″/35.8 mm exit) ≈ 5.6–7.9 kHz: above it a uniform-velocity source does not represent a
  real compression driver, so 8–12 kHz compares **geometries**, not drivers.

## 2. Implemented policy mechanism

`solve.screen_grid` (new, opt-in, screen-only). Absent → every stored grid and hash is
byte-identical. Three forms, exactly one per block:

```yaml
solve:
  screen_grid:
    profile: hf12k_screen_v1        # frozen named list: 500-12000 Hz, 19 log points (~4/oct)
    # or: {lo_hz: 500, hi_hz: 12000, points_per_octave: 6}
    # or: {freqs_hz: [500, 700, ..., 12000]}
```

Refused by the loader, never silently adjusted: a top edge above `target.band_hi_hz`; a profile
whose frozen top exceeds the brief band; `profile` combined with explicit keys; `screen_grid`
together with `solve.freq_grid` or a brief `grid.screen_extra_hz`. `verify`/`final`/`finalist`
keep their frozen grids and extension rules (asserted in `tests/test_config_screen_grid.py`).

`hf12k_screen_v1` is a *frozen explicit list*, not ppo arithmetic at run time, so the solved
frequencies record cannot drift with rounding. It is **not** the default: adopting it for new
high-frequency runs is a config/brief decision (see §5).

## 3. Experiment

Arms (exact lists in `experiment/manifest.json`; each is a real config under `experiment/configs/`):

| arm | intent | freqs | mesh f_max | >10 kHz samples |
|---|---|---:|---:|---:|
| F0 | frozen screen policy under the same 12 kHz brief | 12 (500–10 000) | 10 kHz | 0 |
| F0M | mesh-isolation control: F0 + 12 kHz | 13 | 12 kHz | 1 |
| F1 | uniform ~4/oct | 19 (500–12 000) | 12 kHz | 2 |
| F2 | uniform ~6/oct | 29 | 12 kHz | 2 |
| FA | additive: F0 + 8–12 kHz comb | 21 | 12 kHz | ≥5 |
| FB | hybrid: F1 + the same comb | 27 | 12 kHz | ≥5 |
| F3 | dense independent reference | 53 | 12 kHz | 6 |

Why FA/FB: a uniform log grid at 4 or 6 points/octave places only **two** samples above 10 kHz —
"29 points" buys mid-band density, not HF resolution. FA/FB spend the same budget where the
question is.

**F0 is the frozen 12-point grid scored on the *same* 12 kHz brief — not the deployed 18-point,
8 kHz grid.** The deployed grid belongs to a different brief identity (8 kHz band + extra low/mid
points) and its J is not interchangeable with a 12 kHz-band J; comparing them would conflate the
band change with the sampling change. The deployed baseline is documented in §1.1 instead.

Cohorts (`cohorts.yaml`): 6 designs sampled across the J range of each of four search runs
(`c400` smooth OSSE compact, `room` large room OSSE, `morph` R-OSSE morph, `twinray` rolled
twinray) = **24 distinct designs**, 168 evaluations. Each cohort's brief is copied and extended to
12 kHz (`band_hi_hz`, coverage-profile end anchors, `objective.cd.band_hz`,
`cd.offaxis.band_hz`) as a **new named identity**; `grid.screen_extra_hz` is dropped so F0 is the
frozen 12-point grid exactly. Design hashes are asserted to reconstruct from the stored params.

Mesh convergence (`measure-epw`): the F3 arm at `mesh.epw` 5 / 6 / 8 on two designs per cohort
(room, morph) — upward convergence toward the 24 k dof cap, which the older 7 k cap could not test.

Instrumentation: production `evaluate` (same objective, metrics, cache keys, dataset rows);
`HORNLAB_STAGE_TIMING=1` stage timings; `nvidia-smi` device-dedicated VRAM sampler (WDDM shared
memory is not exposed per process on Windows and is reported as unmeasured); run-dir
`response.npz` for every arm, so the acoustic analysis uses solved bytes, not interpolation of
scores.

Cost expectation from the baseline (median 19 s per 18-freq candidate at 4.1 k dof): F1 ≈ 1.1×, F2
≈ 1.7×, F3 ≈ 3× the current per-candidate solve time; measured numbers replace this in
`GPU_BENCHMARK.csv`.

### 3.1 Mesh/DOF/VRAM preflight (CPU only, before the GPU window)

`experiment/preflight.csv` — the production mesher at each arm's `f_max_hz`, 24 designs × 2 specs:

| arm (f_max) | meshes | ok | refused | quarter DOF | cap | model need (GiB) |
|---|---:|---:|---:|---|---:|---|
| F0 (10 kHz) | 24 | 24 | 0 | 4 563 – 12 911 | 24 000 | ≤1.86 |
| F3 (12 kHz) | 24 | 24 | 0 | 6 423 – **18 439** | 24 000 | ≤2.85 |

Median mesh build 11 s. **No sampled design refuses at 12 kHz**, including the near-limit
18 439-DOF design; the 12 kHz mesh costs ≈1.44× the quarter DOF of the 10 kHz mesh (the expected
area scaling). The calibrated fused-CUDA model (`solve/feasibility.py`, anchors measured at solver
`38e5b1f`) predicts *fit* for all 24 — but that model is not enforced and its 12 kHz-era anchors
were taken with a different probe, so the measured `nvidia-smi` peak is the number that decides
criterion 3. What this rules out is the old 7 k-DOF refusal regime: with the current 24 k caps the
tested classes are not DOF-limited.

**The calibrated model is not trustworthy at 12 kHz, and the preflight proves it.** At 12 183
quarter DOF the anchor table interpolates to ≈1.8 GiB, while the fused ceiling harness measured
**4 744 MiB** for that exact DOF count (`FUSED_CUDA_2026-10-24.md`). A 2.6× under-prediction in the
band that matters means `feasibility.assess` must not become a 12 kHz gate without recalibration;
the `nvidia-smi` peak from the queued jobs is the only admissible capacity evidence here.

## 4. Analysis method

* **J comparison is only within a cohort and only across arms for the same design**, because the
  objective is a band-mean and every arm is scored by the same code on the same mesh family. The
  10 kHz→12 kHz mesh change is isolated by F0M.
* **F0M is an upper bound on the mesh effect, not a clean control.** `mesh_spec.f_max_hz` is
  derived from `max(mode_freqs(...))`, so a 12 kHz mesh that solves only F0's frequencies cannot
  be constructed through the production spec: F0M necessarily adds the 12 kHz sample too. Its
  ΔJ vs F0 therefore mixes (a) the finer mesh at the shared frequencies and (b) one added
  top-edge sample; the sampling-only effect is measured on the same mesh as F1−F0M. Do not read
  ΔJ(F0M−F0) as "the mesh term".
* Ranking: per-cohort Spearman(J_arm, J_F3), top-3/top-5 overlap, recall of the F3 top-3, false
  negatives (F3 top-3 absent from the arm's top-5). Pooled across cohorts only as a mean of
  per-cohort statistics; J is never pooled across briefs.
* HF defects (grid-independent, measured from the dense reference at its solved frequencies):
  on-axis ripple ≥6 dB in 8–12 kHz; local notch ≥6 dB; H-beamwidth at 10–12 kHz ≤0.6× the 1–4 kHz
  median; DI range ≥4 dB across 8–12 kHz. These are **diagnostic flags with stated thresholds**,
  not acoustic verdicts; every flag is reported with its J consequence in `HF_FAILURES.csv`.
  Vertical beamwidth ratio and the throat-impedance swing (max−min of |Z|/ρc in 8–12 kHz) are
  **reported as values, not folded into the defect boolean** — there is no validated threshold for
  them on these typologies, and inventing one would be a false criterion.
  An arm with fewer than 3 solved samples in 8–12 kHz is labelled **unassessable** (it cannot see
  the defect at all), deliberately distinct from "looked and cleared it".

## 5. Pre-registered decision rule (written before reading any measurement)

Adopt a 12 kHz SCREEN default for **eligible new high-frequency runs** only if all hold:

1. **Selection**: pooled mean per-cohort Spearman vs F3 improves by ≥0.10 over F0 **and** top-3
   recall improves or is already 1.0 for both; no cohort loses a true top-3 finalist that F0 kept.
2. **HF defects**: the arm detects at least half of the dense-reference HF defects that F0 misses,
   with no arm-only "defect" that the dense reference does not show.
3. **Cost**: median wall per candidate ≤2.0× F0 on the same designs; median dedicated VRAM delta
   ≤4 GiB; zero refusals/OOM at the tested DOFs.
4. **Physics**: F3 at epw 6 vs 8 changes on-axis SPL by ≤0.5 dB and beamwidth by ≤2° at 10–12 kHz
   for the tested designs; if a class fails this, it is marked unvalidated rather than adopted.

Point-count choice: prefer the **cheapest arm that satisfies 1–3**. If 19 uniform points pass,
`hf12k_screen_v1` (19) is adopted. If only FA/FB pass, the adopted profile is their explicit list
under a new name — uniform ppo would be the wrong knob. If none pass, the default stays 8/10 kHz
and the handback says so explicitly.

Non-goals: no objective weight/formula change (a demonstrated bug would be fixed narrowly and
versioned; none was found in the audit), no mesh-generator change, no historical re-ranking.

## 6. Measured outcome (one screen)

| | F0 (10 kHz) | F1 (19) | F2 (29) | FA (21) | FB (27) | F3 (53) |
|---|---:|---:|---:|---:|---:|---:|
| median wall | 40.3 s | 95.6 s | 147.0 s | 106.8 s | 130.0 s | 268.9 s |
| vs F0 | 1.00 | 2.37× | 3.65× | 2.65× | 3.23× | 6.68× |
| pooled Spearman vs F3 | 0.832 | 0.914 | **0.957** | 0.871 | 0.943 | 1.0 |
| top-3 recall, worst cohort | 0.667 | 0.667 | 0.667 (= F0) | 0.667 | 0.667 | 1.0 |
| HF defects caught (of 6) | 0 (blind) | 5, +1 FP | **6, 0 FP** | 5, +1 FP | 5, +1 FP | 6, 0 FP |
| max dedicated VRAM Δ | 1.4 GiB | 2.7 GiB | 2.7 GiB | 2.7 GiB | 2.7 GiB | 1.9 GiB |

All six HF defects are **beamwidth collapse** at 10–12 kHz (0.46–0.585× the 1–4 kHz width). The
10 kHz grid has fewer than three samples in 8–12 kHz, so it is *unassessable*, not "clean". F2 is
the only 12 kHz arm that passes selection + defect detection, and it still fails the pre-registered
2.0× cost bar; therefore no default change. epw 6 vs 8 at 10–12 kHz: **0.012 dB / 0.12°** over four
designs — the 12 kHz mesh at epw 6 is converged.
