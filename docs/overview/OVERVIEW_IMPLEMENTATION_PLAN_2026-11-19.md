## 1. Non-negotiable rules (read before touching anything)

1. **J is only ranked inside one score identity** (brief + objective version + target set). Never
   aggregate, average or sort J across identities, in Python or JS. (`docs/ACTIVE_STATE.md`.)
2. **Typology grouping follows the knowledge-hub family cards** (`docs/knowledge/README.md`). Do not
   apply one family's heuristics (constant directivity, Keele mouth sizing) to another. A name that
   no card claims stays `unclassified` with a construction label — never guess a family.
3. **Read-only over `runs/`.** The Overview never writes into run folders. GUI-written state lives
   only in `runs/overview/` (phase 3).
4. **No GPU.** Nothing in this plan solves. Snapshot jobs are CPU analysis only and must not take
   `runs/.gpu.lock`.
5. **Interpreter:** `.venv\Scripts\python.exe` always. Tests: `.venv\Scripts\python.exe -m pytest -q <files> -p no:cacheprovider`.
6. **File ownership (CLAUDE.md):** `tools/analysis/**` belongs to the Fable senior lane. Phase 4
   needs changes there → open them as a PR into `hornfab-all-*` or append the exact change to
   `NOTES_FOR_SENIOR.md`. Do **not** edit `docs/plan/**` (frozen).
7. **Another lane has uncommitted edits in `gui/static/app.js`, `app.css`, `hw.js`, `index.html`,
   `glossary.js`.** New UI goes into **new files** (`overview*.js`, `data_overview*.py`). Touch the
   shared files only with the one-line hooks listed per work package, and never reformat them.
8. **Every pushed commit updates `docs/CONTINUITY.md` and `docs/ISSUES.md`** (newest entry on top),
   and every new module/doc gets a row in `docs/CODE_MAP.md` / `docs/INDEX.md` in the same commit.
   Only the parent integrator commits; sub-agents never run git mutations.
9. Every number shown comes from Python. JS formats, filters and sorts; it never derives a ranking.

### WP2.1 Findings engine (Python) — Wave A

**Owner files:** `hornlab_search/gui/data_overview_findings.py` (new),
`tests/test_gui_overview_findings.py` (new).
**Depends on:** phase 1.

Steps:

1. Define a `Finding` dict (use plain dicts + `D.clean`, like the rest of the GUI):
   `{id, kind, subject_type, subject, identity_id, line_key, severity, score, why[], title, detail,
   evidence[], status, resolved_by, first_seen_utc, href}`.
   - `id` = first 16 hex of `sha256(kind|identity_id|line_key|rule_version)` — stable across reloads.
   - `kind` ∈ `budget | refusals | bounds | tie_verify | stale_line | probe_only | registry | software`.
   - `severity` ∈ `critical | high | medium | low` (same words/colours as Readiness).
   - `status` ∈ `open | resolved | superseded` (phase 3 adds `dismissed`, `acknowledged`).
2. Implement `findings(ov: dict, runs: Path) -> list[dict]` that takes the **phase-1 overview
   payload** (do not re-scan runs) plus run dirs for per-run reads. Rules (each a small function
   `_rule_<kind>(...)` returning a list):
   - **budget**: for each ranked line, look at its best run's ndjson (`D.read_ndjson`). Compute the
     best-so-far curve over valid rows; `tail_gain = (best_at_80% - best_final) / best_at_80%`. Open if
     `tail_gain >= 0.01` **and** `n_ok >= min_valid`. **Resolved** if a newer run in the same line
     (later `last`) exists whose first row is after the best run's last row → `resolved_by` = that
     run id. (This is the R4 fix.)
   - **refusals**: line `refused_pct >= 25` → open; severity high if ≥ 40. Detail names the top
     failure kinds (sum `failures` over the line's runs; add a `failures` dict to each line in
     `data_overview.overview` — this one-line addition is allowed in WP2.1).
   - **tie_verify**: identity with `n_tied >= 2` → one finding: "N lines inside one floor; rank them
     with verify solves on the same grid, not more screen evals". Severity high on `current`.
   - **stale_line**: line ranked in the top 3 of a `current` identity whose `last` is > 7 days old →
     low.
   - **probe_only**: line with `probe_only` and ≥ 2 runs → low ("never reached the leaderboard minimum").
   - **registry**: an `unregistered` identity with ≥ 100 evals → medium ("add it to
     score_identities.yaml with its floor").
   - **bounds**: only if `runs/analysis/**/walls_*/walls.json` exists for the line's best run
     (read-only); open per widen proposal. Do not compute walls here.
3. **Ranking** (`score` in 0–100, explainable): `score = 100 * impact * confidence * currency`.
   - impact: rank 1 → 1.0, tie → 0.9, rank 2–3 → 0.7, else 0.4; identity-level findings 0.9.
   - confidence: `min(1, n_ok / 40)`; refusal/registry findings 1.0.
   - currency: identity status current 1.0, unregistered 0.6, diagnostic 0.4, legacy 0.1; × 0.5 if
     line `last` older than 7 days.
   - `why` = list of the three factors as human strings (`"rank 1 in Compact 400"`, `"38 valid evals"`,
     `"current score"`). Sort by `(status != open, -score)`.
4. Dedupe: one finding per `(kind, identity_id, line_key)`. Never one per run.
5. Server: add to `server.py` beside the overview route (one `if` block, 4 lines):
   `GET /api/overview/findings?days=` → `{"findings": [...], "counts": {severity: n}, "generated_utc"}`
   computed from `OV.overview(...)` then `F.findings(...)`.

Acceptance (tests on synthetic run trees like `tests/test_gui_overview.py`):
- a line whose best run is still improving yields one open `budget` finding; adding a later run in
  the same line flips it to `resolved` with `resolved_by` set;
- two lines inside the floor yield exactly one `tie_verify`;
- identical inputs give identical ids and order;
- a legacy-identity finding scores < a current one with the same facts;
- no finding ever compares J across identities (assert each finding has one `identity_id`).

## 6. Known limits of phase 1

- Lines are keyed by construction label, so two genuinely different experiments with the same
  construction under one identity share a line (e.g. all `fold` variants). Accepted for now;
  WP2.1's `resolved_by` uses run order inside the line.
- `unclassified` holds freeform/ellipse/plughorn/ICW/ablation/fidelity probes: no knowledge card
  claims them. Adding a card is research work (`hornlab-typology-research`), not a UI change.
- Cold 14-day load is ~13 s on this machine (WP2.3 fixes it).
- The legacy analysis reports stay as they are; their action list is not yet fed from the findings
  engine.
