# Independent repository findings: Hornfab architecture review

**Inspection:** Live connected GitHub repository, **2026-11-16**, remote `main` head [`913c934d783bed07a2d805d9732dfeedc11b48e4`](https://github.com/llevaachingada/Hornfab/commit/913c934d783bed07a2d805d9732dfeedc11b48e4). Directly inspected source, configs, research/queue documents, GitHub search and recent work. The observations below are *preliminary starting evidence*, not a fresh local execution or claim about an unobserved running job. Recheck the local checkout. Source links pin the GitHub commit unless otherwise stated.

## Findings most likely to change architecture decisions

### 1. The repo **already has a composable generator**, but the search config largely freezes the recipe per run

[`design/generators/registry.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generators/registry.py#L1-L67) defines separate horizontal/vertical profiles, optional profile blending, splice profiles, throat blending, perturbation, mouths and optional native morphing. Its `TYPES` includes conical, exponential, hypex, tractrix, Le Cleac'h, spherical wave, OSSE, splice, spherical salmon, biradial and quadratic-throat waveguide. [`materialize`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generators/registry.py#L242-L360) turns its fixed `generator` block and numeric knobs into a `FREEFORM` design, storing a recipe. The `generator` block, such as which parent profile is used, is not itself the ordinary numeric CMA design vector. This is a **different problem from simply lacking a shared geometry API**.

[`design/generators/grid.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generators/grid.py), [`design/generators/rolled_family.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generators/rolled_family.py), native family schemas and several CAD bridges represent **different geometric domains**. Some surfaces are not faithfully described as two smooth H/V meridians. A single universal H/V law could *reduce* design variety unless carefully scoped.

**Need to investigate:** Do apparently different configs yield geometrically equivalent or near-equivalent acoustically relevant surfaces? Does each generator preserve the source geometry, actual lip shape and mesher validity? Which feature combinations are legally composable rather than just cosmetically similar?

### 2. Shape controls already have documented *inactive* and *conditional* states

[`tools/analysis/parameter_activity.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/tools/analysis/parameter_activity.py) reports searched/fixed/derived/conditional/inactive keys with source predicates and optional sampled-surface perturbation. Its historic ATH report [`parameter_activity.md`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/docs/evidence/bo_study_2026-11-12/b2/parameter_activity.md#L1-L50) found a searched `morph_exponent` **inactive** when `morph_target` was rectangular, so BoTorch's documented active-projection mechanism removed this true no-op. **Do not repeat the historic result as true of every current config**.

[`tools/analysis/geometry_effects.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/tools/analysis/geometry_effects.py) compares geometry sampled from the real mesher API and rejects unsupported non-star-shaped surfaces; it does not independently recreate horn formulas. [`tools/analysis/links.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/tools/analysis/links.py) reports linked-knob correlations/covariance, while production [`search/links.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/search/links.py#L1-L45) handles simple single-level affine links and **explicitly does not support generator blocks**. That is an important gap if broad geometry families become the preferred design.

**Need to investigate:** Why do current knobs collapse to bounds? Which are independent geometric effects versus merely correlated under the existing search? Are there physically meaningful coordinates that make invalid shapes impossible or rare without excluding good horns?

### 3. The current BO adapter is **continuous-only**, despite BoTorch itself supporting mixed optimization

[`bo/encoding.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/bo/encoding.py#L93-L130) explicitly rejects retained discrete/categorical dimensions and uses an active-dimension range of **1–20 continuous controls**. This is a limitation of the **current Hornfab adapter/protocol**, not proof that BoTorch cannot optimize switches. Upstream documents [`optimize_acqf_mixed`](https://botorch.readthedocs.io/en/stable/optim.html) and mixed-alternating optimization. These APIs are possible ingredients, not necessarily a good sample-efficient strategy for a huge hybrid shape space.

[`bo/data.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/bo/data.py) trains on complete observed results (`Y=-J`), excludes fabricated penalty-as-acoustic rows and generates a bounded cheap-checked candidate pool. [`bo/pareto.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/bo/pareto.py) has a coverage/ripple Pareto path; [`bo/turbo.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/bo/turbo.py) handles local BO. A proposed shared-shape BO must define the embedding/encoding, what is observed, which failures enter a separate feasibility model, and exactly which solved designs are compatible.

### 4. There is **material evidence of constraint/refusal inefficiency**, not proof that all refusals are wrong

The Nov 14 [`status report`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/docs/status/2026-11-14/README.md#L11-L22) reports **694 / 2,728 evaluation attempts (approximately 25%)** not reaching the solver across its specified Nov 12 analysis; that is *candidate/search budget*, **not 694 full BEM solves**. It identifies particularly refusal-heavy cells and bound-pinned knobs. Specific older cases are reported in that document and [`HANDOFF_COLLABORATOR_2026-10-27.md`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/docs/HANDOFF_COLLABORATOR_2026-10-27.md), but newer configs/sampling often behave differently.

[`search/outcomes.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/search/outcomes.py#L1-L43) distinguishes complete acoustic score, measured score gate, deterministic geometry/envelope/resource refusal and transient/metric/unknown failure. [`search/cma.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/search/cma.py#L54-L99) already offers strict resampling and bounded attempts. [`design/generated.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generated.py#L180-L207) estimates pre-mesh envelope violation; [`search/evaluate.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/search/evaluate.py#L1038-L1052) grades certain envelope penalties. These are existing partial solutions, **not a blank-slate failure framework**.

**Need to investigate:** Do high refusal rates reflect faulty parameterizations, valid horns beyond owner packaging constraints, insufficient mesher support, resource caps, or genuinely impossible surfaces? What is the *counterfactual discovery gain* from proposed constraint handling?

### 5. The current home objective pursues **specific beamwidth numbers**, despite the owner's broader accepted range

[`targets/spec.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/targets/spec.py#L1-L88) models `coverage_h_deg` and `coverage_v_deg` as scalar targets. The Nov 15 [`home landscape brief`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/examples/briefs/home_landscape_2026-11-15/room_landscape_80x50_700_hf1440_v7.yaml) is 80H × 50V, 350–8000 Hz, FaitalPRO HF1440 idealized source, 700 Hz crossover, 600W × 480H × 480D envelope, with vertical coverage weighted 0.5. The brief's comment says the owner's broader home range was **60–90H, 40–60V**. This is historical context, **not proof of a final newly approved interval**.

[`scalar_v7.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/objective/scalar_v7.py) blends beamwidth error with DI slope, ripple, loading, flatness, diagonal and high-frequency floor terms. It does not implement a generic acceptable-*region* design objective. Changing only target tolerances or score weights would not necessarily solve disconnected lobes, frequency variability or broader listening/room goals. `docs/queue/HOME_SCORE_AUDIT_2026-11-16.md` documents an offline DSP-aware rerank in which the old v7 #1 fell to #12; this demonstrates sensitivity **in a particular case**, not that the experimental score is universally better.

**Need to investigate:** frequency-resolved robust constraints versus integrated objective, truly acceptable coverage ranges, lobing and off-axis leakage, Pareto/QD descriptors, final driver/system metrics. Re-score existing raw responses without altering historical score records where possible.

### 6. There is already an implementation of **quality-diversity**, and it may be underused

[`search/cma_me.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/search/cma_me.py#L1-L44) implements CMA-ME/MAP-Elites with an archive over **mean H/V beamwidth**, rather than merely minimizing one target J. The [Nov 14 report](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/docs/status/2026-11-14/README.md#L88-L94) shows an 18 × 18 archive. **This does not yet establish** that high-quality, diverse candidates survive frequency-resolved HF checks or that QD has been rigorously compared against alternate searches for the user's current goal.

A promising branch of inquiry: represent success as **a repertoire** of horns covering H/V target regions and distinct useful geometries, with cheap constraints and verified physical quality, rather than ask one scalar optimization to choose a single winner. But QD's descriptors and archive cells may themselves encourage pathological designs if defined poorly.

### 7. Historical data reuse is **partly engineered**, not automatically guaranteed by a common label

[`dataset/identity_v2.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/dataset/identity_v2.py#L1-L13) already separates `physical_solve_id`, `analysis_id`, `score_id` and `study_id`. This supports response reuse under new scoring, but **doesn't invent missing high frequencies or correct a different throat/source/boundary model**. [`bo/cohort.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/bo/cohort.py) enforces a strict compatibility gate; [`bo/encoding.py`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/bo/encoding.py#L190-L275) refuses nonrepresentable/clipped historical observations. Broader cross-family statistical reuse **could** be valuable, but needs a valid shared representation and provenance-preserving validation.

### 8. Past cases show **the parameterization can bias the “winning physics”**

[`HOME_LANDSCAPE_PLAN_2026-11-15.md`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/docs/queue/HOME_LANDSCAPE_PLAN_2026-11-15.md) attributes earlier *portrait* horn results largely to a portrait mouth morph and an all-azimuth wall angle, noting a sample of 396 ATH-core designs with only four wider-than-tall geometries and 27 with H beamwidth broader than V. This is strong evidence that search-box choices *can* dominate family ranking. Not all old outputs are acoustically bad; the setup was not exploring the desired landscape space.

The [`HOME_OPTIMIZER_COMPARISON_2026-11-16.md`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/docs/queue/HOME_OPTIMIZER_COMPARISON_2026-11-16.md) correctly warns that existing BO-vs-CMA wins were not equal-information comparisons: BO had 185 historical rows in one experiment; CMA started from a prior best, refusal budgets differed, and seed count was limited. Avoid designing a new architecture around an unreplicated model ranking.

### 9. Current owner work is fragile to concurrent edits; don't create an extra development branch by reflex

[`AGENTS.md`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/AGENTS.md#L1-L20) explicitly overrides older branch/worktree workflows: one canonical checkout, parent integrator controls Git mutations, other agents must preserve concurrent changes. [`NEXT_DEV_PRIORITIES.md`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/docs/NEXT_DEV_PRIORITIES.md) and `docs/CONTINUITY.md` document live study queues, execution pins and pending GUI integration. These are **dated records**, not real-time process status; the local agent must check before doing anything. A scratch **research dossier** is the low-risk path.

### 10. Optional hypothesis from the owner's additional proposal: valid, oversized horns are sometimes precluded from acoustic discovery

The new proposal is reviewed in [`08_OPTION_EXPLORATORY_SIZE_AND_FEASIBILITY.md`](08_OPTION_EXPLORATORY_SIZE_AND_FEASIBILITY.md). Confirmed source paths: [`registry.py#L242-L255`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generators/registry.py#L242-L255) and [`#L304-L307`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generators/registry.py#L304-L307) apply hard generator-envelope checks; [`generated.py#L180-L203`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generated.py#L180-L203) includes a pre-mesh overshoot estimate; [`evaluate.py#L278-L295`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/search/evaluate.py#L278-L295) checks the actual mesh; [`bo/data.py#L1068-L1155`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/bo/data.py#L1068-L1155) excludes out-of-envelope cheap-pool candidates. These can indeed prevent learning acoustic behavior *outside* the current product envelope, but this alone does not prove those candidates are worth solving.

**Specific mathematical caution verified:** [`grid.py#L2986-L3016`](https://github.com/llevaachingada/Hornfab/blob/913c934d783bed07a2d805d9732dfeedc11b48e4/hornlab_search/design/generators/grid.py#L2986-L3016) uses `max_phi radius` to assign **both** W and H on the generic GRID route, intentionally conservative. An asymmetric horn can therefore look too tall to this estimator. Whether actual eligible designs are falsely refused requires a measured CPU surface-versus-mesh comparison. An axis-corrected algorithm must also handle oblique petal/ridge extrema and full 3D shell bounds. Its rows and rolled-family paths use other methods.

**Alternative research direction:** Keep the 600 × 480 × 480 mm home envelope as the final shippable product requirement, while comparing its current hard enforcement with a versioned, compute-capped exploratory data study and/or offline acoustics-versus-size Pareto analysis. Collect true W/H/D, frequency-resolved acoustic metrics and simulation cost separately. Potential wins: identify true physics-versus-size tradeoffs and avoid premature size pruning. Potential losses: GPU cost, invalidity from meshing larger shapes, irrelevant oversized successes, confounded brief comparisons and too many search dimensions. No exploration ceiling or percentage of GPU budget has been approved.

## Alternative architectures Fable must compare, not assume

1. **Minimal unified scientific interface, separate families**: keep trusted analytic and grid/CAD generators; consolidate parameter semantics, feasibility accounting, data identity, flexible scoring and model selection, rather than a single mega-family.
2. **Hierarchical composable geometry grammar**: named, valid physical primitives; family/feature choices in an outer tier, continuous knobs in inner optimizers; strong compatibility and inactive-control semantics.
3. **Shared constrained freeform/shape basis**: smooth or piecewise-appropriate morphable geometry, with known reference horns as seeds, using geometry descriptors for transfer. Requires proof that it represents difficult folds/rollback and source joins without corrupting surfaces.
4. **Quality-diversity-first design discovery**: keep several geometry generation paths, archive high-quality designs over coverage/shape descriptors, refine selected elites with BO/CMA, judge with a flexible performance region.
5. **Intermediate option**: leave geometry almost unchanged, fix incorrect/fixed briefs, outcome errors and feasibility sampling, then measure whether a costly architectural redesign is even warranted.

6. **Separate acoustic discovery and size-aware selection (optional)**: treat manufacturability/home envelope as a product preference or independent constraint during discovery, with controlled oversize studies and a size-vs-acoustics archive. Compare against the lower-cost possibility of correcting conservative geometry estimates first.

**Cross-cutting hypotheses:** learned feasibility, multi-fidelity/reduced-order acoustic gates, robust beamwidth regions, interactive preferences and existing-result reuse. These can pair with different architecture choices, but should not be prescribed in advance.

## External primary source leads (review scope, not proof of fit)

- [BoTorch optimizer API and mixed-domain acquisition](https://botorch.readthedocs.io/en/stable/optim.html) and [input vs outcome constraints](https://botorch.org/docs/next/constraints): credible mechanisms, but require Hornfab integration and experimental validation.
- [BoTorch constrained BO tutorial](https://botorch.org/docs/v0.17.2/tutorials/closed_loop_botorch_only) and [scalable constrained Bayesian optimization](https://archive.botorch.org/tutorials/scalable_constrained_bo): feasibility can be modeled separately from acoustic performance.
- [pyribs official documentation](https://docs.pyribs.org/en/latest/index.html) and [CMA-ME tutorials](https://docs.pyribs.org/en/latest/tutorials.html): direct grounding for Hornfab's existing quality-diversity code.
- [BoTorch tutorials](https://botorch.org/docs/tutorials): compare custom BoTorch orchestration with user-facing experiment frameworks, not assume a new hand-written BO scheduler is necessary.
- [ATH OS-SE published waveguide paper](https://at-horns.eu/release/OS-SE%20Waveguide.pdf), [ATH CORE](https://www.at-horns.eu/core.html), [Keele's bi-radial patent](https://patents.google.com/patent/US4308932A/en): published shapes/constraints must be studied before claiming a hybrid is physically faithful.
- [Anthropic on just-in-time context and specialized subagents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) and [incremental handoff for long-running agent projects](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents): motivates a small index plus evidence files and clear staged deliverables.

## What this review did **not** establish

- No local `git status`, process list, saved `run.json` inventory, or actual external agent state was inspected. Remote `main` may be behind local work.
- No GPU/CPU acoustic comparison was newly executed; quoted results are from the repo's dated evidence documents. Local cheap investigators should use available data to reproduce key numbers when practical.
- Not enough evidence yet to claim that a master family, hierarchical model, QD or BO will outperform existing lanes on **verified acoustic quality per GPU-hour**.
- The right physical audible/listening goal for this owner remains a design choice and needs critical validation, not an arbitrary generic “perfect horn” score.

## Supplement: v3 adaptive search and queue audit (GitHub `main` 2c0e2928e932, November 16, 2026)

This later review should supersede earlier statements that the repo has **no** watchdog or live queue capabilities. Existing code already has a stop-on-refusal/stall/bound-pin watchdog (`tools/run_campaign_night.py` ~84–213), save-on-stop/partial-result handling (~1002–1123), a safe live queue reload with PAUSE/STOP/admission (~1232–1422), and a separate advisory per-run `tools/analysis/optimizer_switch.py`. Read-only status exists in `tools/night_status.py`. `tests/test_night_runner_watchdog.py` and `tests/test_night_runner_live.py` cover relevant existing behaviors. Link: [2c0e2928e932](https://github.com/llevaachingada/Hornfab/commit/2c0e2928e932a47975fc284401eafa74ebfc5002).

The currently missing *verified capability* is a scientific resource-allocation policy: deciding whether a stall reflects objective error, geometry/mesh refusal, hard physical boundary, poor parameterization, convergence, or a genuine opportunity to switch methods. A stalled best `J` alone does not determine it. BoTorch's scalar/TuRBO/Pareto studies have strict admission and typed training requirements (`hornlab_search/bo/{policy,data,cohort,encoding,turbo}.py`), and `hornlab_search/search/cma_me.py` values QD archive additions that scalar stop rules can miss. Historical BO/CMA outcomes in `docs/queue/HOME_OPTIMIZER_COMPARISON_2026-11-16.md` are **not** an equal-information, equal-cost proof of universal BO superiority. Separate measured data from a model's hypothetical action. The new investigative options and exact source links are in `09_OPTION_ADAPTIVE_SEARCH_SUPERVISOR.md`; local investigators should refresh actual checkout/run state.
