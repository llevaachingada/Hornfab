# System data export (HORN + VENTED-WOOFER)

Portable, regenerable export of the system solve/screen store. `system_runs/` is git-ignored, so a
cloud agent (or a reviewer without the machine) cannot read the system study from a checkout. This
directory is the committed, deterministic view of it.

Generated by [`tools/data/system_cases.py`](../../tools/data/system_cases.py) from the canonical
checkout (`C:/Users/hunte/Hrns/hornlab-search`). Re-run it after any system run/screen changes:

```powershell
.venv\Scripts\python.exe tools\data\system_cases.py --root . --out docs\system_data --pretty
```

Do **not** hand-edit the generated files; re-run the tool. `README.md` (this file) is the only
hand-written artifact here.

> **Pure-horn GPU design export is elsewhere.** This bundle covers the *system* study (horn channel
> + vented woofer box, Boundary Lab coupling, screen shortlists). The per-typology top-N GPU-solved
> horn designs with acoustic arrays are exported by [`tools/data/top_designs.py`](../../tools/data/top_designs.py)
> into [`docs/top_designs/`](../top_designs/). The two are deliberately separate: system cases have
> no objective `J` to rank, and their fidelity labels are declared, not scored.

## Files

| File | Contents |
|---|---|
| `system_cases.csv` | One flat row per system case, 53 stable columns. No absolute paths. |
| `system_cases.json` | The same rows plus nested `run`/`metadata` detail, the scan census, the readiness registry block, and `diagnostics`. |
| `system_screens.json` | Every woofer screen (`system_runs/**/woofer_seed.json`): study id, counts, input hashes, envelope and the shortlist rows verbatim. |

All three are LF-only UTF-8. `system_screens.json` is intentionally JSON-only: the shortlist rows are
nested objects and a CSV would flatten them lossily.

## CLI

```
--root PATH      repository root (default: `.`)
--out PATH       output directory, relative to --root (default: docs/system_data)
--no-csv         skip system_cases.csv
--no-screens     skip the screen scan (also removes a previously generated system_screens.json)
--pretty         indent the JSON files
--strict         exit 1 if any diagnostic exists (invalid case, hash mismatch, unusable registry)
--quiet          do not print the census summary
```

Exit `0` on success. `--strict` exits `1` when the diagnostics list is non-empty; without it the
export still succeeds and records every problem in `diagnostics`. The tool is read-only over
`system_runs/`, writes only under `--out`, uses only the standard library (PyYAML is imported behind
a guard for the readiness registry), and never imports a solver or Boundary Lab module.

## What comes from where

| Kind | Source | Examples |
|---|---|---|
| **Facts** | the case directory | `solved`/`staged`/`refused`, frequencies, backend, box mm, horn offset, clearance, hashes |
| **Declarations** | `docs/research/system_woofer_2026-11-18/readiness.yaml` | `fidelity`, `transducer_shape`, `gate`, `ref`, `evidence`, `pair_with`, `horn_source` |

Fidelity is **never inferred**. A case absent from the registry is `fidelity: UNDECLARED` even when
its manifest contains motor/geometry blocks. `motor` is the one exception: when undeclared, an
observed `motor_mapping` / `motor_role` in the manifest yields `motor: real` and
`motor_source: manifest`. Status facts never come from the registry.

## Case schema (`system_cases.csv` / `.json`)

Rows are one timestamped case directory under `system_runs/system/<experiment>/<case>/`
(`^YYYYMMDDTHHMMSSZ`), sorted by `(experiment, case)`.

| Column group | Columns |
|---|---|
| identity | `experiment`, `case`, `case_key` (`<experiment>/<case>`), `created_utc`, `kind`, `source_path` |
| declaration join | `gate`, `gate_source`, `ref`, `fidelity`, `motor`, `motor_source`, `transducer_shape`, `horn_source`, `pair_with`, `evidence`, `notes`, `declared` |
| status | `status` (`solved`/`staged`/`refused`/`invalid`), `solved`, `run_status`, `stage_ok`, `stage_error` |
| run | `n_frequencies`, `freq_min_hz`, `freq_max_hz`, `backend_id`, `solve_kind`, `phasor_convention`, `completion` (`done/total`) |
| provenance / integrity | `authorized_by`, `project_sha256`, `project_integrity`, `run_manifest_sha256`, `run_manifest_integrity`, `request_sha256`, `request_integrity`, `manifest_payload_sha256`, `manifest_integrity` |
| box / horn | `box_width_mm`, `box_height_mm`, `box_depth_mm`, `net_volume_l`, `net_volume_source`, `port_area_cm2`, `tuning_hz`, `horn_mesh`, `horn_mesh_sha256`, `horn_offset_mm`, `horn_offset_mm_xyz`, `clearance_status`, `clearance_min_mm`, `driver_name` |

Absent values are `null` in JSON and empty in CSV. In the JSON each row also carries:

* `run` - `present`, `status`, `schema`, `schema_version`, `started_at_utc`, `finished_at_utc`,
  `frequencies_hz`, `excitation_port_ids`, `solver_options`, `engine_runs`, `meshes`,
  `completion_mask` (`{done,total,complete}`).
* `metadata` - `box_source`, `clearance_source`, `sources` (the ordered file list that was walked).

### Status rules (first match wins)

1. `solved` - `run/manifest.json` exists on disk **and** its `status` is `complete`.
2. `refused` - a case-level refusal: `payload.result.ok is false` with a refusal error (driver/port
   clearance, panel fit, "does not fit"), `refused: true`, or a `REFUSED` / `BL_*REFUS*` token in a
   payload string.
3. `staged` - a readable manifest with no complete run.
4. `invalid` - missing/unparseable manifest or an unreadable case directory. A malformed case is a
   row with `status: invalid` plus a `diagnostics` entry; it never stops the export.

Deliberate exclusions from the refusal test: the per-field ledger `spec.geometry.refusals`
(`GEOMETRY_FIELD_UNAVAILABLE`) and the generic capability status `BL_CAPABILITY_OK` are **not** case
refusals. Only a case-level refusal marks a case refused.

### Integrity

* `manifest_integrity` - `verified` when the sha256 of the canonical payload matches the recorded
  `manifest_payload_sha256`, `mismatch` otherwise, `unknown` when no hash is recorded. The
  canonicalisation (sorted keys, floats rounded to 12, JSON-encoded payload values re-parsed once) is
  reproduced from `hornlab_search.system.contracts.canonical_json` /
  `hornlab_search.system.provenance.load_manifest` with the standard library only, so the tool can
  verify manifests without importing the system package.
* `run_manifest_integrity` - verified against the recorded `payload.run.manifest_sha256`.
* `project_integrity` / `request_integrity` - verified against the case's `case.blab.json` /
  referenced request file when present; `file_missing` when the record names a file that is not in
  the case directory.

### Metadata extraction

Box, horn, driver and port numbers are found by **walking keys**, not by fixed positions: the
ordered sources are `request.json`, `run/request.json`, `run/compiled-system.json`,
`run/project.snapshot.blab.json`, then `adapter_spec.json`, `case.blab.json`, `stage_report.json`,
`driver_patch_report.json`, any other `*request*.json`/`*spec*.json`, and finally the manifest
payload. The first declared value wins and the source is reported in `metadata.sources`. This is why
staged cases (which have no `run/` tree) still carry box/horn numbers.

* `net_volume_l` - a declared `net_volume_l` (`net_volume_source: declared`), else the mesh
  `air_volume_m3` converted to litres (`net_volume_source: air_volume_m3`), else `null`.
* `horn_offset_mm` - the largest absolute component of the case's horn `translation_mm` list; the raw
  three-component vector is kept as `horn_offset_mm_xyz`. It is the case's own model translation, not
  a delta against another case.
* `driver_name` - `driver_name`, else `mapping.driver_id`, else `driver.yaml.name`, else `driver_id`.
* `clearance_status` - `pass` / `violation` / `not_recorded` from an explicit clearance block (a
  `clearance` object with `status`/`ok`/`min_gap_m`). `unknown` when the case has no readable
  metadata. A seeded *placement gap scan* (`seed.placement.min_clearance_mm`) is **not** a clearance
  verdict and is not used.

## Screens schema (`system_screens.json`)

Top level: `tool`, `schema_version`, `generated_utc`, `source`, `census`
(`files`, `unique_study_ids`, `duplicate_study_ids`, `shortlist_rows_total`, `kept_rows_total`),
`diagnostics`, `studies`.

Each study: `study_id`, `path` (repo-relative), `created_utc` (if the file records one), `mtime_utc`,
`size_bytes`, `schema`, `system_objective_version`, `claim`, `input_sha256`, normalized `counts`
(`drivers_loaded`, `drivers_rejected`, `boxes_considered`, `boxes_rejected`, `candidates_kept`,
`pareto_front_rows`, `shortlist_rows`, `placements_considered`, `placements_rejected`,
`xo_hypotheses`, `xo_rejected`, `bl_panel_fit_rejected`), `catalog_driver_ids`,
`catalog_count`, `envelope`, the count of `shortlist`/`kept_rows`/`rejected_ledger`, and the
`shortlist` rows verbatim (all fields as written by the screen).

## Grouping and caveats

* **Not a ranking.** System cases carry no scalar objective. `objective`/J does not exist here and
  the rows must not be sorted by "quality". Screens declare `claim` explicitly
  ("heuristic fixed-horn screen; no scalar winner; not a validated ranking") - respect it.
* **Declared fidelity.** `COUPLED_VENTED_FEM_BEM_LEM` means the horn channel is an ideal
  normal-velocity source (no compression-driver absolute SPL) and the transducer shape is BL's
  provider default. Do not present these as absolute system SPL.
* **Frequency coverage.** Solved runs start at 200 Hz (the short W3 smoke run at 250 Hz); nothing
  below that is solved, so box tuning is not visible in the responses (`freq_min_hz` says so).
* **Clearance is a recorded verdict, not a replay.** This tool never imports the Boundary Lab
  clearance module, so `clearance_status` is `not_recorded` unless a case wrote an explicit
  clearance block. In particular the 0 mm horn-offset staging case
  (`bl_ref_case/20261118T231100Z-assembly-62864-f62bf799`) has no clearance record in its own bytes;
  the R16 "horn rear inside the enclosure front plane" finding lives in the readiness note/handoff,
  so the export reports `staged` + `not_recorded` rather than asserting a violation. The GUI can
  replay the geometry check; this portable export cannot and must not guess.
* **Invalid rows are data.** Two `bl_ref_case` timestamped directories have no `manifest.json`; one
  `two_way_80x50_700_pilot` manifest fails its recorded payload hash. They are exported as
  `invalid` / `mismatch` with diagnostics so the gap is visible, not hidden.
* **Snapshot census (regenerated on every run).** At the last generation (after the 2026-11-19
  system-evidence queue plus the real-motor assembled and two refined-mesh cases):
  **54 timestamped case dirs in 26 experiments** (51 with a manifest), `solved 19`, `staged 29`,
  `refused 3`, `invalid 3`; readiness still declares 9 of the original cases; 6 screens in 6 files
  over 2 study ids with 36 shortlist rows. The new `ev_*` experiments are `UNDECLARED` by design
  (they are evidence runs, not readiness-registry cases).

## Determinism and safety

Cases sort by `(experiment, case)`; screens by repo-relative path; column order is fixed; JSON key
order is insertion order. Only `generated_utc` changes between runs on an unchanged tree. Paths are
repo-relative (the `system_runs` junction is not resolved, so the export stays portable). The tool
never writes outside `--out` and never spawns a subprocess.
